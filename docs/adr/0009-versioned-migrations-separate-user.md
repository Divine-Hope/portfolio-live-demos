# 0009. Versioned migrations, applied by a user only they run as

Date: 2026-10-05
Status: Accepted

## Context

The schema was one file of `CREATE ... IF NOT EXISTS` statements, applied by ingest on every start. That can create a database but never change one: edit a table definition, rerun, and the old table stays while the log says "schema up to date". It also meant ingest, a long-running process reading the public internet, held the right to alter and drop tables.

## Decision

- Migrations are numbered files in `src/livedemos/db/migrations/`, applied in order, each once, and recorded in `schema_migrations` with their name and a checksum of their statements (full-line `--` comments don't count; inline ones do). Changing an applied migration is refused; a change is a new file.
- Before anything runs, `migrate` refuses a database that has migrations this code doesn't know (an older build over a newer schema) and a ledger with a version recorded twice.
- One run at a time: `CREATE TABLE schema_migrations_lock`, without `IF NOT EXISTS`, is atomic, so exactly one run gets it, and it's dropped when the run ends. A crashed run leaves it, and every later run refuses until someone checks and runs `migrate --unlock`.
- `0001_initial.sql` is the old schema, still all `IF NOT EXISTS`, so on a database from before this decision it's a no-op that records the baseline. Checked on the local stack's existing data: 1 recorded, 2 applied, rows untouched.
- ClickHouse has no transactional DDL. A migration that fails halfway runs again from the top, so every statement must be safe to repeat (`IF NOT EXISTS`, `MATERIALIZE`).
- A one-shot `migrate` job runs first, as a new `migrator` user. `ingest` can now only select and insert; `api` only select. `tests/integration/test_storage.py` connects as each real user and checks what it's refused.

## Consequences

- Schema changes ship like code: a file, a review, a test from the old schema to the new (`test_an_existing_database_upgrades_in_place`).
- One more secret (`clickhouse-migrator-password`, generated by Terraform like the others). It must exist in SSM before the first deploy that needs it, so apply Terraform first.
- No down-migrations. Deploying a build older than the schema fails at `migrate`, before ingest or the API start on a schema they don't know; the old containers keep running. Undoing a migration is a new forward one.
- Revisit if a second service needs its own schema, or if migrations need to run while ingest keeps writing to a table they rewrite.
